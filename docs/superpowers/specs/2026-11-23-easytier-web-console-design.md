# EasyTier Web 管理台（新前端）设计

日期：2026-11-23
状态：待确认（已根据审阅意见和生产环境核查结果修订）

## 1. 意图与背景

用户自建了 EasyTier 的 easytier-web 管理服务（中央网络模式），对原版前端不满意：

- Dashboard 只有几个数字和两张预览列表，基本没有用处；
- 设备列表的设计一般（表格和卡片两种视图，展开行、抽屉层层嵌套）；
- EasyTier 支持一台设备加入多个网络，原版界面按「多网络」来设计交互，
  但用户的实际用法是**一台机器只在一个网络里**，每次操作都要多选一次网络或实例，负担过重。

目标是做一个**独立的新前端**，完全替代原版的界面。后端仍使用上游原版的 easytier-web，本项目不改它的代码。

**生产环境现状（2026-11-23 在 `idc-ucloud` 上只读核查）**：
- 线上运行的是 easytier-web **2.6.4**（commit `8428a89d`，2026-05-12），比本地上游 main（`45a6b6f1`）落后 235 个提交。
  部署方式是 Docker 容器 `easytier-web`（镜像 `easytier/easytier:latest`，入口命令 `easytier-web-embed --disable-registration`），
  数据目录 `/home/flintylemming/appdata/11211,22020-easytier-web/data/et.db`。
  同一台机器上还有一个 `easytier-core 2.6.4` 容器，以设备身份接入这个管理台。
- 2.6.4 只有「每台设备各自配置网络实例」这一种模式：没有中央网络，也没有别名、拉黑、凭据等接口。
- 数据：共 3 个用户，所有实例都属于用户 FlintyLemming（user_id 3）。一共 42 台设备、46 个实例；
  38 台设备只有 1 个实例，4 台有 2 个。按网络名分成两组：
  - **组 A**：42 个实例，其中 4 个已停用。全部是固定 IP。组网方式不统一：34 个用 PublicServer（公共服务器地址有好几种），8 个用 Manual（peer 地址各不相同）。
    1 个实例单独配置了 ACL，11 个有子网代理，1 个有端口转发。其余高级选项（路由、socks5、监听地址、各种开关）在设备之间各有不同。
  - **组 B**：4 个实例，全部停用，全部用 DHCP，全部配置了 ACL。

**用户的决定**：先把后端升级到支持中央网络的版本，再使用**中央网络模式**。
规划阶段核实到：中央网络模式已经包含在官方发布的 **v2.7.1** 中（2026-11-16，`0d9c52b1`），本地 main 只比它多 11 个提交，其中 3 个涉及 easytier-web，都是小改动：可选的 `config_server_host` 字段、建网时可以自定义密钥、导航显示成员数。
所以**升级目标定为官方 v2.7.1 发布版**（Docker 镜像 `easytier/easytier:v2.7.1`），不用还没发布的 main。新前端以 v2.7.1 的接口为准，并兼容 main 新增的可选字段。这样一来，本项目除了新前端，还要多做两件事：
1. 一份后端升级的操作手册（§5.10.1）；
2. 一个**迁移向导**，把这些旧实例转换成中央网络和成员（§5.10.2）。
   上游的数据库迁移只会新建中央网络相关的空表，不会转换旧实例。

## 2. 目标、非目标、反目标

### 目标

1. **无损迁移**：不修改后端代码，新前端只调用上游 main 已有的 `/api/v1/*` 接口，新旧前端可以同时运行。
   从 2.6.4 迁移到中央网络的整个过程中，每台设备迁移前后的有效配置都要**逐项对比**：
   能原样保留的必须保留；中央网络表达不了的差异（见 §5.10.2），必须在执行前的预览里逐条列出，用户确认后才能执行。
   全过程可以回滚。
2. **功能全覆盖**：原版前端在中央网络模式下的所有功能，新版都要有入口（用户确认这些都在用）：
   成员细项（固定 IP、子网代理、主机名覆盖、高级配置覆盖）、ACL 策略、凭据与临时节点、
   设备上的手动实例（含 VPN Portal、TOML 导入导出）、节点诊断（peer、路由、ACL 命中、日志级别、运行中的 TOML）。
3. **默认网络优先**：凡是和网络相关的界面，都直接显示设备的「默认网络」。
   「加入第二个网络」和「手动实例」只放在设备详情右上角的网络切换器里。
4. **有用的 Dashboard**：地图显示节点分布，并能处理大量机器集中在同一个城市的情况；
   另有关键数字、「需要关注」列表和「连接质量」列表。
5. **视觉遵循 `DESIGN-cursor.md`**：奶油色底、暖墨色文字、细线分隔、无阴影；
   标题字重 400，代码类内容用等宽字体；橙色只用于唯一的主按钮。

### 非目标（v1 不做）

- 不修改后端代码，不新增接口（数据库结构的变化只来自上游自带的迁移）。
- 深色主题（设计规范只有浅色）。
- 完整支持 webhook 模式（`--webhook-url`），只做降级处理，见 §6.9。
- 事件历史和趋势图：后端没有存储历史数据，前端也不做持久化。

### 反目标（即使能跑起来，出现以下情况也算失败）

- 保存配置时**丢字段**：界面没显示的字段被清空或改成了默认值。
- 页面向第三方发请求：地图瓦片、IP 定位 API、Google Fonts、统计脚本等一律禁止，所有资源都要自托管。
- 把多网络的复杂度带回主流程：在设备列表或详情的主路径上出现「先选网络」「先选实例」这类步骤。
- 橙色泛滥，或者为了好看加阴影、粗体大标题。

## 3. 约束（从原版代码中确认的事实）

- **API**：基础路径是 `/api/v1`，用 cookie 会话（`withCredentials`），401 时跳转登录。
  登录和注册时，密码要先在前端做 **MD5** 再提交（原版就这么做，必须保持一致，否则旧账号无法登录）。
  可参考原版 `frontend/src/modules/api.ts`，里面有全部接口和类型。
- **运行模式**：`GET /console-info` 返回 `webhook_auth`。值为 `false` 时是中央网络模式，也是本设计的目标模式。
- **设备**：`GET /machines` 返回每台设备的 `info`（主机名、版本、运行中的实例、`device_os`）、`alias`、
  `client_url`（公网地址）、`location`（`{country, region?, city?}`，GeoIP 解析出的**中文名**，**只有在线设备才有**）、
  `networks`（`[{network_id, display_name, network_name}]`）、`online`、`last_seen`。
- **内网 IP**：设备列表接口不返回内网 IP，需要对每个网络调用 `GET /networks/{id}/members`，
  从成员数据里取（`virtual_ipv4` 是固定 IP，`allocated_ipv4` 是自动分配的，`runtime_virtual_ipv4` 是运行时实际的 IP），
  然后按 `device_id` 拼到设备上。
- **中央网络成员的实例 ID 等于 `network_id`**：节点诊断走 `POST /machines/{machine}/proxy-rpc`，
  `instance.id` 填 `network_id`（原版 `NetworkDetail.vue` 就是这么用的）。
- **GeoIP**：后端内置的库（`geoip2-cn.mmdb`，132KB）只覆盖中国。国外 IP 的 country 返回「海外」，内网 IP 返回「本地网络」。
  用户可以在启动后端时加 `--geoip-db` 指定 GeoLite2-City 库，这样国外节点也能解析到城市（这只是启动参数，不改代码）。
- **网络配置类型**：原版的 `NetworkConfig` 等类型来自 protobuf 代码生成
  （`frontend-lib/scripts/codegen-proto.mjs`，读取 `easytier-proto/proto/*.proto`，用 `@protobuf-ts`），
  另外还有 `normalizeNetworkConfig` 和 `toBackendNetworkConfig` 两个兼容转换函数（`frontend-lib/src/types/network.ts`、`networkCompat.ts`）。
- **TOML 互转**：后端提供 `POST /parse-config`（TOML → 配置对象）和 `POST /generate-config`（配置对象 → TOML），这两个接口不需要登录。
- **许可证**：EasyTier 使用 LGPL-3.0。从 `frontend-lib` 复制的代码（类型、兼容转换、登记命令拼装等）保留原版权声明。
  本项目整体按 LGPL-3.0 发布，或至少把复制过来的文件当作 LGPL 部分对待。

## 4. 方案比较（已选定方案 2）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 1. Vue + 复用原版复杂组件 | 复制 `frontend-lib` 整个库，继续用 PrimeVue 的配置表单、ACL 编辑器等，只新写外壳和新页面 | 最快做到功能齐全 | 弹窗里是 PrimeVue 的视觉，产品里有两套风格；继续依赖 PrimeVue |
| **2. Vue + 全新界面，只搬逻辑** ✅ | 只复制不涉及界面的逻辑（类型、兼容转换、API 客户端），所有界面按 Cursor 规范重写；高级配置用「常用字段表单 + TOML 编辑」两种模式 | 视觉统一，代码完全自有，体积小 | 工作量最大的是配置表单 |
| 3. React + shadcn 重写 | 全部推倒重来 | 生态更大 | 工作量和方案 2 一样大，但用不上任何现有的 Vue 逻辑 |

用户选择了**方案 2**。

## 5. 已决定的部分

### 5.1 部署与迁移

- 构建产物是纯静态文件（`dist/`）。
- 推荐部署方式：在同一个域名下，用 Caddy 或 Nginx 托管 `dist/`，并把 `/api/` 反向代理到原版 easytier-web 的 API 端口（默认 11211）。
  这样前后端同源，cookie 不会遇到跨域问题。
- 只支持**同站**部署。原版后端的会话 cookie 是 `SameSite=Lax`，并且没有设置 `Secure`，
  所以前端和 API 如果在两个不同的站点（不同的注册域名），浏览器发请求时不会带上 cookie，没法登录。
  前端和 API 在同一注册域名的不同子域时（比如 `console.example.com` 和 `api.example.com`），可以通过运行时读取一个可选的 `/config.js`
  （`window.__ET_CONFIG__ = { apiBase: "https://…" }`）指定 API 地址；没有这个文件时默认同源。README 里推荐同源方案，并说明这个限制。*（实现者的判断）*
- **OIDC**：后端登录成功后，只会跳转回一个前端地址（`--oidc-frontend-base-url`，没设置时是 `/`）。
  README 要写明：如果新前端和 API 同源，不用额外设置；如果新前端在别的地址，需要把这个参数指向新前端。
  这样一来，原版前端就没法同时接收 OIDC 登录了，但用户名密码登录不受影响。*（实现者的判断）*
- 仓库需要提供：`deploy/Caddyfile` 示例、`deploy/docker-compose.yml` 示例（原版 easytier-web 加上托管新前端的 Caddy），
  以及 README 里的**迁移步骤**：
  1. 原版 easytier-web 保持运行，数据库不动；
  2. 部署新前端，配置好 `/api` 反向代理；
  3. 用原来的账号登录；
  4. 原版前端（如果是 embed 版本，就在原来的 web 端口）可以继续保留，作为回退和对照。
- 路由用 hash 模式（`/#/devices`），任何静态服务器都不需要额外配置。

### 5.2 技术栈

- Vue 3 + Vite + TypeScript、vue-router（hash 模式）、Pinia（存储会话信息、console-info，以及设备、网络、成员聚合后的数据）、vue-i18n（zh-CN / en，默认按浏览器语言）。
- 样式：Tailwind CSS v4，把 `DESIGN-cursor.md` 的 token 写成 CSS 变量和 Tailwind 主题。
  交互原语（Dialog、Popover、DropdownMenu、Tabs、Tooltip、Toast）使用无样式组件库 **Reka UI**，外观全部自己写。
- 字体：Inter（代替 CursorGothic）和 JetBrains Mono，通过 `@fontsource/*` 自托管，不走 CDN。
- 地图：`d3-geo` + `topojson-client` + `world-atlas`（Natural Earth 数据，打包进产物），渲染成 SVG 点阵。不使用瓦片地图。
- protobuf 类型：把需要的 `.proto` 文件复制到本仓库 `proto/` 目录（在 README 里注明来自 EasyTier 哪个 commit），
  从 v2.7.1 tag 复制，沿用原版的 `@protobuf-ts` 生成脚本生成 TS 类型，并提供 `pnpm codegen` 命令方便以后跟随上游更新。
- 测试：Vitest 测纯逻辑；Playwright 测页面，用拦截的假 API 数据（做法同原版 `frontend/tests/dashboard.test.mjs`），
  另外再对一台真实的 easytier-web 做一次冒烟测试。

### 5.3 信息架构与路由

顶部横向导航（高 56–64px，奶油色背景），从左到右：Logo（橙色 ◆ + EasyTier）｜概览 · 设备 · 网络｜右侧依次是
「添加设备」（全站唯一的橙色主按钮，点开是一个浮层，显示登记命令和复制按钮）、铃铛（被拉黑的设备仍在尝试连接时显示角标）、头像菜单（修改密码、切换语言、退出登录）。

| 路由 | 页面 |
|---|---|
| `/login`、`/register` | 登录和注册，行为和原版一致：用户名密码、验证码、开启注册时显示注册入口、开启 OIDC 时显示对应按钮 |
| `/` | 概览（Dashboard） |
| `/devices` | 设备列表 |
| `/devices/:machineId` | 设备详情，显示**默认网络** |
| `/devices/:machineId/networks/:networkId` | 设备详情，显示某个非默认网络（从网络切换器进入） |
| `/devices/:machineId/instances` | 该设备的手动实例（高级） |
| `/networks` | 只有一个网络时**直接跳转**到这个网络的详情；否则显示网络列表和「新建网络」 |
| `/networks/:networkId` | 网络详情，分为成员、ACL、凭据（仅安全模式）、设置几个标签页 |
| `/migrate` | 从 2.6.4 旧实例迁移到中央网络的向导（§5.10.2）。只在还有旧实例时，从概览页的横幅进入 |

### 5.4 默认网络规则

- **主网络**：成员数最多的网络；成员数相同时，取 `/networks` 返回顺序中的第一个。
- **设备的默认网络**：设备在主网络里，就是主网络；否则取设备 `networks` 列表中的第一个。
- 不在任何网络里的设备，没有默认网络，界面上显示「未加入网络」，并给出「加入 {主网络}」按钮。

### 5.5 Dashboard（mockup：`dashboard-full.html`）

从上到下：

1. **标题**「概览」（display-lg，字重 400），下方一行小字「每 10 秒自动刷新」。
2. **四个数字卡片**（一行四格，用细线分隔）：
   - 在线设备 `18 / 20`，下方注明离线台数；
   - 网络数，下方注明主网络的名称和网段；
   - **P2P 直连率**，下方注明「N 条连接中 M 条走中继」；
   - **可更新**台数，下方注明「最新版本 x.y.z」。
3. **节点分布地图**（用户选的是 B 方案，mockup：`map-layout-v2.html` 中的 B）：
   - 左侧是地图，右侧是按位置的排行，每行显示城市、比例条和「在线/总数」，最后一行是「本地网络 / 无公网位置」。
   - 地图默认**自动聚焦**：取所有已定位节点，计算出覆盖大部分节点的最小区域（例如去掉离群点后剩下约 80% 的节点），
     视野对准这片区域，并留出边距。视野外的节点，在地图对应的边缘显示小标签，比如「← 法兰克福 1」。
     右上角有「聚焦 / 世界」切换，点边缘的小标签也会切到世界视图。
   - 同城的节点合并成一个圆点：圆点面积随台数变化，台数大于 1 时在圆点上显示数字。
     在当前视野下，像素距离太近的圆点再合并一次，标签写成「上海 等 2 地」。
     全部离线的地点画成空心圆。
   - 鼠标悬停在圆点上时，弹出这个地点的机器列表（状态、名字、内网 IP），最多 6 行，超出部分写「还有 N 台」；
     点击圆点则跳到设备列表，并按这个地点筛选。
   - 「连接线」开关：用弧线连接两两之间有连接的地点，实线表示 P2P 直连，虚线表示中继。默认打开。
   - 地图上的点阵、圆点和连线只用墨色和灰色，**不用橙色**。
4. **两栏**：
   - **需要关注**（最多显示 5 条，有「全部 →」入口）：被拉黑后仍在尝试连接的设备（带「解除拉黑」按钮）、
     还没加入网络的设备（带「加入 {主网络}」按钮）、离线超过 24 小时的设备、版本落后的设备（合并成一条）。
   - **连接质量**：最慢的 5 条连接，显示两端设备、方式（「中继 · 经 X」或「P2P · UDP/TCP/QUIC…」）和延迟。
     右上角汇总中继和直连的数量。

### 5.6 设备列表（mockup：`device-list.html` 中的表格部分）

- 页面标题「设备」，副标题是「N 台设备 · M 台在线 · K 台待加入网络」。
- 工具栏：搜索框（匹配名称、主机名、内网 IP、公网 IP、城市）；筛选标签「全部 / 在线 / 离线 / 未加入网络」，各带数量；
  从地图跳过来时，再多一个可以关闭的「位置：上海」标签。
- 表格列：
  1. **设备**：别名或主机名（14px，字重 500），下一行小字写系统（来自 `device_os`）。有别名时，系统后面再跟上主机名；
  2. **内网 IP**：默认网络中的 IP（等宽字体，鼠标悬停时出现复制按钮），下一行小字写网络名；
     设备加入了多个网络时，后面加「· +N 个网络」。设备未加入网络时，这一格显示「未加入网络」和「加入 {主网络}」小按钮；
  3. **位置 · 公网 IP**：城市名，下一行用等宽小字写公网 IP；
  4. **版本**：等宽字体。版本落后于当前设备中的最高版本时，加一个「可更新」小标签；
  5. **最后在线**：绿点加「在线」，或灰点加相对时间（「2 天前」）；

  - **诊断**（默认折叠）：日志级别（读取和设置）、ACL 规则命中统计、当前运行的 TOML 配置（只读，可复制）。

### 5.10 从 2.6.4 迁移

#### 5.10.1 后端升级手册（放在 `docs/upgrade-runbook.md`，由用户执行，或者在执行当天得到用户明确同意后再执行）

1. **前置验证**（在本机完成，不碰生产环境）：用官方 v2.7.1 镜像启动 easytier-web，加载**生产数据库的副本**启动；
   再用 **2.6.4 版的 easytier-core** 接入，确认下面几点：
   - 旧实例照常下发和运行；
   - 设备能自动登记到 `devices` 表；
   - 中央网络的配置能下发给 2.6.4 的 core 并运行起来。

   原因：上游代码里有针对老版本 core 的兼容分支（`support_config_source` 等），但没有专门针对 2.6.4 core 的测试。
   如果这一步不通过，就需要先把 42 台设备的 easytier-core 升级。这会成为单独一项工作，到时要先回来找用户确认。
2. 停止 `easytier-web` 容器，备份整个数据目录（`et.db`、`et.db-wal`、`et.db-shm`）。
3. 用 `easytier/easytier:v2.7.1` 镜像（或用户镜像站 `mirror-hub.flinty.moe` 上的同一版本）启动，数据卷和启动参数保持不变（`--disable-registration`）。
4. 检查：原版内嵌前端能登录；设备陆续重新连上；旧实例照常运行。
5. 部署新前端（§5.1），用原来的账号登录。
6. 运行迁移向导（§5.10.2）。
7. **回滚**：恢复第 2 步的备份，换回 2.6.4 镜像。注意升级之后在后端做的所有修改都会丢失，所以第 6 步之前，可以随时零成本回滚。

#### 5.10.2 迁移向导（新前端里的 `/migrate` 页面）

- **入口**：当前用户名下还有旧实例时，概览页顶部显示一条横幅：「检测到 N 个旧版网络实例，可以迁移到中央网络」。
  旧实例指的是 instance id 不等于任何中央网络 id 的实例。
- **第 1 步 盘点**：按网络名把实例分组。每组显示实例数、停用数、在线数，以及设备是否已经登记到新后端
  （设备登记以后才能被添加为成员；还没重新连上的设备，标记为「等待上线」）。
  停用的实例**默认不迁移**，作为手动实例原样保留（组 B 全部是这种情况）。
- **第 2 步 网络设置**：每一组对应生成一个中央网络的草稿。
  显示名默认用网络名；网络名和密钥取组内最常见的值，如果不一致就列为冲突；
  组网方式和服务器地址取组内最常见的值，但用户可以改成别的，比如 Manual 模式加上所有服务器地址的合集；
  网段由 `network_length` 和各设备的固定 IP 推算出来。
- **第 3 步 逐台预览**：对每台设备，把旧配置拆成三类，用差异视图展示：
  1. **转换成成员字段**：`virtual_ipv4` 写成固定 IP，`hostname` 写成主机名覆盖（只在和设备自己的主机名不同时），
     `proxy_cidrs` 写成子网代理；
  2. **转换成配置覆盖**：去掉中央网络掌管的字段后，剩下的所有字段里，值和默认值不同的，原样放进 `config_override`。
     比如路由、socks5、端口转发、监听地址、MTU、各种开关；
  3. **中央网络无法表达，会改变**：中央网络掌管的字段如果和网络级设置不同，就会被网络级设置替换。
     这些字段是 dhcp、`network_length`、网络名、密钥、组网方式、`public_server_url`、`peer_urls`/`peers`、`secure_mode`、`acl`
     （依据：上游 `central_network/compiler.rs` 里的 `apply_member_override`）。
     每一条都要高亮显示。按现有数据，至少会出现：组网方式和服务器地址与网络设置不同的设备，以及单独配置了 ACL 的那 1 台设备。
     **ACL 不做自动转换**：显示旧 ACL 的内容，提示用户迁移完成后，到网络的 ACL 页手动写成中央规则。
  用户可以对每台设备单独选择「迁移」或「暂不迁移」（暂不迁移的设备，保留为手动实例）。只有当所有标为第 3 类的差异都已勾选确认，才能进入下一步。
- **第 4 步 执行**：先把所有将要迁移的旧实例配置导出成一个 JSON 文件，让用户下载保存。然后**逐台设备**依次执行：
  1. 停用旧实例（`PUT …/networks/{inst}` 设置 `disabled: true`，这一步可以撤销）；
  2. 添加为成员，并设置成员字段和配置覆盖；
  3. 等待成员进入运行状态（`running === true`，有超时）；
  4. 确认运行后，删除旧实例。

  任何一步失败，都要对这台设备做回滚：把它移出网络，重新启用旧实例。然后在页面上报告失败原因，接着处理下一台。
  向导可以中途退出，下次进入时从上次的进度继续（已经是成员的设备会自动跳过）。
  采用「先停用、再添加」的顺序，是为了避免同一台设备上，同一个网络名同时跑着两个实例，造成 IP 冲突。
- **第 5 步 校验报告**：对每台在线设备，读取运行中的 TOML（`show_node_info`），和旧配置经 `generate-config` 生成的 TOML 做对比，
  去掉第 3 类里已经确认的差异以及 instance id 之后，应该**完全一致**。不一致的设备列入报告，并给出「回滚这台」的按钮。
  离线的设备标记为「等待上线后校验」，下次打开向导时补做校验。
- 向导要能对着**生产数据库的副本**和本地启动的后端完整演练（§8）。

## 6. 行为细节

### 6.1 数据加载与轮询

- 用 Pinia store 维护一份聚合数据：machines、networks、每个网络的成员，以及由此计算出的设备视图模型（默认网络、内网 IP、位置等）。
- 轮询间隔：设备列表和设备详情 5 秒，概览 10 秒，peer 和路由 15 秒（只在概览和设备详情页拉取）。
  页面不可见时（`document.hidden`）暂停，切回来时立刻刷新。同一时刻每类请求只能有一个在进行中。
- 拉取 peer 时，对所有在线成员并发调用 `proxy-rpc`，**并发上限是 4**；单个请求超时或失败时，跳过这个节点，不影响整体。

### 6.2 地理定位（名称 → 坐标）

- 前端内置一张坐标表（构建时生成并打包，gzip 后控制在 150KB 以内），内容包括：
  中国省级行政区和地级市（中文名，同时匹配带「省/市/自治区/特别行政区」后缀和不带后缀的写法）、
  世界各国的中心点（中英文名），以及世界主要城市（中英文名，覆盖 GeoLite2 中常见的城市名）。
  数据来源用 GeoNames 或 Natural Earth，需要遵守相应许可（GeoNames 是 CC-BY，需在关于页署名）。
- 匹配顺序：国家加城市 → 国家加省/州 → 国家中心点 → 归入「未定位」。
  「本地网络」单独计数；「海外」或匹配不上的，计入「未定位」，在排行最后一行显示。
- **离线设备的位置**：每台设备最后一次在线时的位置，按 `machine_id` 缓存在 localStorage 里。
  离线设备用缓存的位置画成空心点；没有缓存的，计入「未定位」。

### 6.3 版本「可更新」

- 版本号取 `easytier_version` 中 `-` 之前的 `x.y.z` 部分，和所有设备里的最高版本比较，低于最高版本就标记为可更新。
  不访问外网检查最新版本。

### 6.4 连接判断（P2P 还是中继）

- 对某台设备在网络 N 中的实例（instance id = N）：
  - `list_peer` 返回的 `peer_infos` 中，有未关闭连接的 peer，算作**直连**。
    方式取连接的 `tunnel.tunnel_type`（如 udp、tcp、quic、wg），延迟取 `stats.latency_us`，流量取 `rx_bytes/tx_bytes`。
  - `list_route` 中其他目标的路由，如果 `next_hop_peer_id ≠ peer_id`，算作**中继**，「经 X」中的 X 是下一跳对应的主机名，延迟取 `path_latency`。
- 把 peer 对应到设备时，用路由里的 `ipv4_addr` 去匹配成员的 `runtime_virtual_ipv4`，匹配不上再用 `hostname`。
  匹配不上任何成员的节点，分两种情况：
  - 能和 `GET /networks/{id}/members` 返回的 `temporary_peers` 对上（按 `peer_id` 或 IP），就是**临时节点**，加「临时」标签；
  - 其余的都算**基础设施节点**，包括 Gateway 模式下 easytier-web 自带的网关节点、PublicServer 和 Manual 模式下的公共或自建服务器。
    显示时标为「网关」或「服务器」，主机名照原样显示。*（实现者的判断）*
- **直连率** = 直连的设备对数 ÷ 所有可达的设备对数，**只统计成员与成员之间的连接**；基础设施节点和临时节点都不计入，也不在地图上画线。
  每对设备只算一次；只要有一端报告了直连，这一对就算直连。经过网关或服务器中转的连接，显示为「中继 · 经 网关」或「中继 · 经 服务器」。
- 地图连线和「连接质量」列表都使用同一份计算结果。

### 6.5 写操作与「不丢字段」

- 成员相关修改只发送**变化的字段**（`PATCH /networks/{id}/members/{device}`）。
- **子网代理和配置覆盖**：后端的 `PATCH proxy_cidrs` 实际是写进成员的 `config_override`（覆盖对象原来不存在时，先建一个空的默认对象）。
  所以 `has_override` 为真，**不代表**用户改过高级配置。处理方式：*（实现者的判断）*
  - 设备详情页单独读取这个成员的配置覆盖（`GET …/config`），去掉 `proxy_cidrs` 之后，和默认对象比较：
    有其他字段不同，才显示「已覆盖」，否则显示「默认」。
  - 「恢复默认」：子网代理为空时，调用 `DELETE …/config`；子网代理不为空时，调用 `PUT …/config`，内容是一个**只带当前 `proxy_cidrs` 的默认对象**。
    这和后端自己创建覆盖对象的方式完全一样，一次请求就能完成，子网代理不会丢。确认弹窗里写明「子网代理会保留」。
  - 高级配置编辑器保存时，同样要把当前的 `proxy_cidrs` 带上。
- 修改 ACL 时，以读取到的完整策略对象为基础，只改动用户编辑的部分，然后整体写回。
- 网络配置对象的读写，必须经过移植过来的 `normalizeNetworkConfig` 和 `toBackendNetworkConfig`。
  表单只修改它展示的字段，其余字段原样保留。
- 每个写操作都要有加载状态、成功提示和失败提示（失败时显示后端返回的 `message`）。
  删除、移出、吊销、重新生成密钥等危险操作，都需要二次确认。

### 6.6 高级配置编辑器（成员覆盖和手动实例共用）

- 「表单 / TOML」两个标签页。
- 表单：只放常用字段。具体包括哪些字段由实现者参考原版 `Config.vue` 决定，至少要有：
  监听地址、MTU、延迟优先、加密和压缩、KCP/QUIC 代理、端口转发、DNS 相关选项、VPN Portal 客户端。
- TOML 模式：打开时调用 `generate-config`，把当前对象转成 TOML 显示；保存时先调用 `parse-config` 解析，再按正常保存流程提交。
  解析失败时，在编辑器下方显示错误，不能提交。
- 切换标签页时同步数据：从 TOML 切回表单时，先解析，失败则停留在 TOML 页。

### 6.7 手动实例（高级）

对应原版的 `RemoteManagement`：列出设备上的实例（`GET /machines/{id}/networks`，**排除 instance id 等于中央网络 id 的实例**）；
可以新建（高级配置编辑器 + 从 TOML 导入）、启用或停用、删除；查看运行状态（`networks/info/{inst}`）；
管理 VPN Portal 客户端（获取信息，以及增删客户端）；导出 TOML。

### 6.8 添加设备、拉黑设备

- 「添加设备」浮层：移植原版 `enroll.ts` 的拼装逻辑，生成 `easytier-core --config-server {proto}://{host}:{port}/{username}`。
  旁边配一句说明：「在设备上运行这条命令，设备登记后会出现在设备列表中，再加入网络即可」。
- 铃铛浮层：列出被拉黑的设备、尝试连接的次数和最后尝试的时间，可以解除拉黑。

### 6.9 webhook 模式降级

`console-info.webhook_auth === true` 时：隐藏「网络」导航和所有中央网络相关的界面；
设备详情只显示「手动实例」和概览；页面顶部提示「当前后端运行在 webhook 模式，部分功能不可用」。

### 6.10 风险

- **2.6.4 的 core 能否在中央网络模式下正常工作**：还没有验证，见 §5.10.1 第 1 步。如果不行，就得先升级设备端，范围会明显变大。
- **跨版本升级**：生产环境要从 2.6.4 直接升到 v2.7.1（正式发布版）。缓解办法是先在副本上演练，并保留可以回滚的备份。
- **中央网络是同构模型**：每个网络只能有一种组网方式、一组服务器和一套 ACL。现有设备在这些方面并不统一，迁移会带来行为变化，
  比如部分设备的引导节点会改变。只能靠预览确认和迁移后的校验来控制。
- **迁移会删除旧实例**：所以要先导出 JSON、做好数据库备份，并且逐台确认运行正常后，才删除这台设备的旧实例。

## 7. 留给实现者决定的部分

- 组件拆分、store 的具体结构、文件布局。
- 地图「自动聚焦」用的具体算法（离群点怎么判断、边距多少），只要效果和 mockup B 一致即可。
- 坐标表的生成脚本和精确的数据范围（在 150KB 以内）。
- 高级配置表单里具体包含哪些字段（在 §6.6 的最低要求之上）。
- 空状态、加载骨架屏、错误提示的具体文案和样式（遵循设计规范）。
- 中英文文案。

## 8. 验收要点

- **迁移演练**：拿生产 `et.db` 的副本，在本机用 main 后端加载，再接入几个 2.6.4 的 core 模拟设备，完整走一遍升级和迁移向导：
  预览里列出的第 3 类差异和 §1 中核查到的情况吻合；执行后校验报告没有意外差异；
  分别验证「单台回滚」和「整体回滚（恢复备份 + 换回 2.6.4）」都能恢复到原来的状态。
- 在升级后的后端上，新前端登录后，设备、网络、成员、ACL、凭据都显示正确。
  在新前端里修改任意一项，再到上游内嵌的原版前端查看，结果一致，并且没有字段丢失。
- 只有一个网络时，从设备列表点进设备，再到看到连接和设置，中间不出现任何「选择网络」或「选择实例」的步骤。
- Dashboard 在 20 台左右的设备规模下，地图聚焦、合并、悬停、边缘标签和连线都正常工作；没有任何节点被定位时，地图显示合理的空状态。
- 浏览器网络面板中，除了本站和 API，没有其他请求。
